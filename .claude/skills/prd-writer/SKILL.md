# PRD Writer

## When to invoke

**Trigger on:**
- "PRD를 써줘 / 작성해줘 / 만들어줘"
- "기능 스펙 / 제품 스펙 / 요구사항 문서"
- "이 기능 정의서 만들자"
- "write/draft/create a PRD"
- 사용자가 새 제품·기능을 설명하면서 문서화를 원하는 경우

**Do NOT trigger on:**
- 일반적인 제품 관련 Q&A ("이 기능 어떻게 구현해?")
- 단순 기획 토론
- 회의록 작성 (별개)
- 이미 존재하는 PRD에 대한 단순 코멘트

## 핵심 원칙

이 스킬은 **정확도가 속도보다 우선**합니다. 다음 원칙을 어기지 마세요.

1. **인터뷰가 먼저** — 사용자의 의도를 캐묻기 전에 PRD 본문을 작성하지 않습니다. 사용자가 "그냥 다 알아서 써줘"라고 해도 최소한 Step 1, 2의 핵심 질문은 반드시 진행합니다.
2. **빈칸 환각 금지** — 사용자가 주지 않은 정보는 채워넣지 않습니다. KPI 목표치, 출시일, 사용자 수, 예산, 인력 등은 절대 만들어내지 말고 `🟡 [확인 필요]`로 명시.
3. **추정 마킹** — 추론한 내용은 반드시 `🔸 [추정: 근거]` 형태로 표시. 사용자가 컨펌하면 마킹 제거.
4. **사용자 표현 보존** — 문제 정의, 사용자 페인포인트, 핵심 가치 제안은 사용자의 원문 표현을 그대로 인용. 멋대로 의역하지 않습니다.
5. **Non-goal 명시** — 무엇을 "안 할지"를 반드시 별도 섹션으로.
6. **섹션 단위 진행** — 전체 PRD를 한 번에 쏟지 않고 한 섹션 작성 → 사용자 확인 → 다음 섹션.

## Workflow

### Step 0: 범위 파악 (AskUserQuestion)

먼저 어떤 종류의 PRD인지 물어봅니다. AskUserQuestion으로:

> "어떤 종류의 PRD를 작성할까요?"
> - 새 제품 PRD (full product) — `template-product.md` 사용
> - 기능 PRD (existing product 안의 feature) — `template-feature.md` 사용
> - 내부 도구 PRD (internal tool) — `template-feature.md` 사용

선택에 따라 적절한 템플릿을 `Read`하여 사용합니다.

### Step 1: 문제와 사용자 인터뷰 (필수, AskUserQuestion 2~3번)

다음 토픽을 빠짐없이 다룹니다. 한 번에 1~3개 질문씩 묶어서.

| 카테고리 | 핵심 질문 |
|----------|-----------|
| **Who** | 이 제품/기능의 주 사용자는 누구? 1차/2차 페르소나? |
| **Pain** | 사용자가 지금 겪고 있는 페인포인트는? 현재는 어떻게 해결하고 있는지(workaround)? |
| **Why now** | 왜 지금 만들어야 하나? 미루면 무슨 일이 일어나나? |
| **Trigger** | 어떤 상황/맥락에서 이 기능을 쓰게 되나? (jobs-to-be-done) |

답변을 받으면 한 줄로 요약해서 사용자에게 다시 보여주고 "이렇게 이해해도 될까요?" 확인.

### Step 2: 목표와 비목표 인터뷰

| 카테고리 | 핵심 질문 |
|----------|-----------|
| **Goals** | 성공이 어떤 모습? 측정 지표가 있다면? (없으면 그대로 두기) |
| **Non-goals** | 이번 버전에서 명시적으로 **안 할** 것은? (이게 잘 안 나오면 더 물어보기) |
| **Constraints** | 기술적 제약, 시간, 예산, 컴플라이언스, 의존성? |

`🟡 [확인 필요]`를 적극 사용. 사용자가 모르는 건 모르는 채로 둠.

### Step 3: 요구사항 인터뷰

| 카테고리 | 핵심 질문 |
|----------|-----------|
| **Must have** | 이 기능이 동작한다고 말하려면 반드시 있어야 할 것은? |
| **Nice to have** | 있으면 좋지만 V1에서 빠져도 되는 것은? |
| **User stories** | "사용자로서 ~을 하고 싶다, 왜냐하면 ~" 형식으로 핵심 시나리오 3~5개 |
| **Edge cases** | 잘못될 수 있는 시나리오? 어떻게 처리해야 하는지 사용자가 정한 게 있는지? |

### Step 4: 섹션 단위 작성

Step 0에서 고른 템플릿을 따라 **한 섹션씩** 작성합니다. 각 섹션 작성 후:

1. 사용자에게 보여줌
2. "이 섹션 OK? 빠진 거나 고칠 거 있어?"
3. 피드백 반영 후 다음 섹션

`🔸 [추정]`이나 `🟡 [확인 필요]`가 들어간 곳은 사용자에게 명시적으로 확인 요청.

### Step 5: 최종 리뷰

PRD 전체를 한 번 더 훑으면서:
- 모든 `🟡 [확인 필요]` 항목을 별도 섹션 "Open Questions"로 모아 표시
- 모든 `🔸 [추정]` 항목 리스트업, 사용자에게 최종 컨펌
- 누락 가능성 체크리스트:
  - [ ] 문제와 사용자가 명확한가
  - [ ] Non-goals가 있는가
  - [ ] 측정 가능한 성공 지표 또는 `🟡` 마킹이 있는가
  - [ ] User stories 또는 핵심 시나리오가 있는가
  - [ ] Edge case가 다뤄졌는가
  - [ ] Open questions 섹션이 있는가
  - [ ] 의존성/리스크가 있는가

### Step 6: 파일로 저장

사용자가 OK 사인을 주면 다음 위치에 저장:

```
docs/prd/YYYY-MM-DD-<slug>.md
```

(`docs/prd/` 디렉토리가 없으면 생성)

- 새 제품 PRD → `.claude/skills/prd-writer/template-product.md`
- 기능 PRD / 내부 도구 → `.claude/skills/prd-writer/template-feature.md`

스킬을 호출하면 위 파일들을 `Read`해서 구조를 따르세요.

## 자주 빠지는 함정

1. **인터뷰 건너뛰기** — 사용자가 자세히 설명했더라도 Step 1~3 질문은 반드시 진행. "혹시 더 추가하실 내용 없으세요?" 식으로라도.
2. **목표 환각** — "MAU 10% 증가" 같은 숫자를 사용자가 안 줬는데 만들지 마세요. `🟡 [확인 필요]`로.
3. **Non-goal 누락** — "이건 안 한다"는 명시가 없는 PRD는 합격이 아닙니다.
4. **너무 큰 첫 PRD** — 첫 버전은 짧게. 50줄 안에 들어오게. 사용자가 더 깊게 가자고 하면 그때 확장.
5. **이미 결정된 것처럼 쓰기** — 미정인 것들은 미정으로. "TBD", "🟡", "Open question" 적극 사용.

## 출력 톤

- 한국어 (사용자가 영어로 요청했으면 영어)
- 격식체 vs 평어 — 사용자가 평어를 쓰면 평어로 맞춥니다
- 마크다운 헤더, 표, 체크리스트 적극 사용
- 이모지는 마킹용(🔸🟡✅)만 사용
